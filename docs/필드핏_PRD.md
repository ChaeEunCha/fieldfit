# 필드핏(FieldFit) PRD (Product Requirements Document)

| 항목 | 내용 |
|---|---|
| 제품명 | 필드핏(FieldFit) |
| 문서 상태 | Draft v1 — 해커톤 예선 프로토타입 + 본선 확장 대비 |
| 근거 문서 | `docs/필드핏_통합기획문서.md` (문제정의·시장분석·기획서·기능명세서·정책서 통합본) |
| 대상 독자 | 개발 팀(프론트/백엔드), 디자이너, 심사위원 |

> 이 PRD는 통합기획문서의 내용을 "무엇을, 왜, 얼마나 만들 것인가"에 집중해 실행 가능한 형태로 재구성한 문서입니다. 산출 공식·기준값의 원본 수치와 상세 근거는 통합기획문서 Ⅳ부(정책서)를 따릅니다.

---

## 1. 배경 및 문제 정의

초보 귀농인은 전국 공통 표준 생육 매뉴얼("사과는 15~25°C, 물 관리 중요")만 참고해 재배를 시작하지만, 정작 실패의 결정적 원인은 지역 고유의 토양(pH 등)·기상(야간 저온 등) 변수에 있다. 흙토람·기상청 데이터가 공개돼 있어도 pH·EC·유효인산 같은 전문 용어라 해석이 어렵고, 이를 "내 땅에 이 작물이 맞는지"로 변환해주는 진단 도구가 없다.

기존 서비스는 이 공백을 메우지 못한다.
- **팜모닝**: 시세·보조금·병해충 정보·커뮤니티 중심, 개인화 환경 진단 없음
- **그린대로**: 정책·주거·일자리 정보 통합, 작물별 환경 적합도 진단 없음

→ **필드핏의 포지셔닝**: "정보 제공"이 아니라 "내 땅 + 내 작물 + 지금 시점"을 계산한 **의사결정 지원**.

(상세 근거·시장 규모·경쟁사 분석: 통합기획문서 Ⅰ부 1~4장)

## 2. 제품 목표

| 목표 | 설명 |
|---|---|
| 핵심 목표 | 귀농인이 재배 예정 작물의 환경 적합도를 지역·시기 단위로 정량 진단받고, 위험 시점을 선제적으로 인지하게 한다 |
| 차별화 목표 | "5작물 비교", "위험 캘린더 알림", "리포트 근거 챗봇" 3가지 기능으로 경쟁 서비스가 다루지 않는 "판단" 영역을 선점한다 |
| 이번 단계(예선) 목표 | 실 백엔드·API·LLM 연동 없이, 더미데이터 기반 클릭형 프로토타입으로 문제-해결 스토리를 시연 영상으로 전달한다 |

### Non-goals (이번 단계에서 하지 않는 것)
- 실제 공공데이터 API(기상청·농경지 토양정보) 연동 — 본선 이후
- 실제 LLM(Claude API) 연동 — 본선 이후
- 회원가입/로그인, 실제 개인정보·위치정보 수집
- 이메일/푸시 알림 실제 발송
- 5작물·특정 지역 외 확장

| 페르소나 | 핵심 니즈 | 필드핏 사용 방식 |
|---|---|---|
| **메인 — 김도현(34)**, 귀농 1년 차, 전북 고창, 사과 재배 준비 | 표준 매뉴얼만으로 모르는 지역 리스크를 미리 알고 싶음 | 지역·작물 입력 → 적합도 확인 → 위험 캘린더 알림 등록 |
| **서브 — 박은주(52)**, 귀농 준비 중, 지역·작물 미확정 | 여러 지역·작물 후보를 비교해 의사결정에 참고하고 싶음 | 5작물 비교 매트릭스 탐색 → 챗봇에 추가 질문 |

(상세 페르소나: 통합기획문서 5장)

## 4. 범위 (Scope)

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| **예선 (이번 스프린트)** | Next.js/React 클릭형 프로토타입, 전 기능 더미데이터 기반, .ics 생성만 실제 동작 | 메인 시나리오(온보딩→적합도→매트릭스→리포트→챗봇→캘린더) 시연 영상 촬영 가능 |
| **본선** | 기상청 단기예보·농경지 토양정보 API 실연동(최소 1개 작물), 산출 로직 실제 계산 | 실데이터로 F3 적합도 점수가 산출되고 결과가 정책서 공식과 일치 |
| **이후 확장** | Claude API 실연동(F5 리포트·F6 챗봇), 5작물 전체 실데이터, 이메일/푸시 알림 | LLM 응답이 22장 정책(리포트 근거 범위)을 준수 |
| **장기** | 대상 작물/지역 확대, 실사용자 피드백 기반 로직 고도화 | 별도 로드맵 수립 |

이번 PRD는 **예선 범위**를 1차 실행 대상으로 하되, 아래 기능·데이터 요구사항은 처음부터 본선 확장을 염두에 두고 설계한다(예: mock 데이터와 실제 데이터를 같은 인터페이스로 다루도록 구조화).

## 5. 기능 요구사항

### 5.1 기능 목록 (우선순위 MoSCoW)

| ID | 기능명 | 우선순위 | 예선 구현 방식 | 본선 구현 방식 |
|---|---|---|---|---|
| F1 | 온보딩(지역·작물·시기 입력) | Must | 실제 입력 폼 + 더미 지역/작물 목록 | 동일 (실 데이터 조회 트리거로 연결) |
| F2 | 공공데이터 연동 표시(기상·토양) | Must | 더미데이터를 "연동 중" 애니메이션으로 표시 | 기상청·농경지 토양정보 API 실호출 |
| F3 | 환경 적합도 산출 결과 | Must | 정책서 공식으로 사전 계산한 더미 점수 표시 | 동일 공식을 실데이터에 실시간 적용 |
| F4 | 5작물 환경 적합도 비교 매트릭스 | Must | 5작물 더미 점수를 매트릭스/레이더로 표시 | F3 로직을 5작물에 반복 적용 |
| F5 | LLM 재배 가이드 리포트 | Must | 사전 작성 리포트 텍스트, "생성 중" 연출 | Claude API로 F3 결과 기반 리포트 생성 |
| F6 | 컨텍스트 챗봇 | Must | 예상 질문 3~5개 더미 Q&A 매칭 | 리포트를 컨텍스트로 주입한 LLM 질의응답 |
| F7 | 위험 경고 캘린더(.ics) | Must | 더미 위험일자로 .ics 파일은 **실제 생성** | 실데이터 기반 위험일자로 동일 로직 사용 |
| F8 | 알림 수신 시점 설정 | Should | UI 옵션 선택 + .ics VALARM 반영(실제 동작) | 이메일/푸시 발송 채널 추가 |
| F9 | 마이페이지/진단 이력 | Could | 더미 이력 리스트 2~3건 | 실제 사용자별 이력 저장 |

### 5.2 사용자 플로우 (메인 시나리오)
1. 지역(전북 고창)·작물(사과)·재배 예정 시기 입력 (F1)
2. 기상·토양 데이터 "연동 중" 화면 (F2)
3. 적합도 점수·등급·핵심 리스크 확인 (F3)
4. 5작물 비교 매트릭스에서 다른 작물과 비교 (F4)
5. LLM 재배 가이드 리포트 확인 (F5)
6. 리포트 하단 챗봇에 추가 질문 (F6)
7. 위험 경고 캘린더에서 저온 위험일 확인, 알림 시점 선택 후 .ics 다운로드 (F7, F8)

### 5.3 기능별 요구사항 요약
> 각 기능의 입력/처리/출력/예외처리 전체 스펙은 통합기획문서 15장(기능 상세 명세) 참고. 아래는 개발 착수를 위한 핵심 요약만 정리.

- **F3 산출 로직**: 종합 점수 = 온도 적합도×0.6 + 토양 적합도×0.4 (0~100점). 등급: 매우적합(85+)/적합(70+)/보통(50+)/주의(30+)/부적합(29 이하). → 통합기획문서 19장
- **F7 위험 판정**: 저온/고온/토양 병해 3가지 트리거 조건 → 통합기획문서 20장. 알림 옵션: 당일/1일 전(기본)/3일 전/7일 전.
- **F5/F6 LLM 정책**: 리포트는 F3 결과만을 근거로 생성, 챗봇은 리포트 범위를 벗어난 질문에 "근거 밖" 안내 후 대체 채널 유도 → 통합기획문서 22장
- **작물 기준값(18장)**: 사과·배·오이·감자·상추 5종의 적정 온도·pH·위험 임계값은 잠정치이며 본선 전 농촌진흥청 자료로 검증 필요

## 6. 비기능 요구사항

| 구분 | 요구사항 |
|---|---|
| UI/UX | 전문 용어 최소화, 초보자 눈높이 문구, 모바일 우선 반응형 |
| 성능(본선 기준) | 공공데이터 API 응답 지연 시 로딩 상태 명시, 3초 이상 지연 시 대체 안내 |
| 접근성 | 위험/적합 등급을 색상만으로 구분하지 않고 아이콘·텍스트 병기 |
| 데이터 신뢰성(본선 기준) | 리포트 하단에 기준값 출처(농촌진흥청 등) 명시 |
| 프로토타입 제약 | 모든 데이터는 정적 더미 JSON, 새로고침해도 값 일관성 유지 |
| 개인정보(본선 기준) | 위치정보는 적합도 산출 목적으로만 사용, 별도 개인정보처리방침 필요 |

## 8. 리스크 및 가정

| 리스크/가정 | 대응 |
|---|---|
| 작물별 기준값(18장)이 잠정치 | 본선 착수 전 농촌진흥청 표준영농교본으로 재검증 |
| 기상청·토양정보 API 응답 지연/결측 | 20.4절 정책대로 캐시·인근지역 대체값 사용 (본선에서 구현) |
| LLM 응답이 리포트 범위를 벗어난 내용을 생성할 가능성 | 22장 정책대로 프롬프트에 F3 결과만 근거로 명시, 범위 밖 질문은 정형 응답으로 대체 |
| "검증되지 않은 니즈"(경쟁사 부재가 곧 수요 증명은 아님) | MVP 이후 실사용자 반응 검증 필요 (통합기획문서 4.3절) |
